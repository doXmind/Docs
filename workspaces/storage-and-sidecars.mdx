---
title: "Local storage and sidecars"
description: "Understand Markdown Page sidecars and preserve legacy Attachment recovery evidence."
---

Your source files stay in the folders you choose. A Markdown Page has a same-name hidden JSON sidecar for lossless editor HTML and replaceable UI state. The Markdown source remains authoritative and readable without that sidecar.

If a Page sidecar is missing, opening the Page imports the Markdown source into the rich editor without creating a sidecar. The first actual content edit and save creates a fresh sidecar from the current editor state; simply opening the Page or pressing `Cmd+S` without a content change does not. Rich details that had no exact Markdown representation cannot be reconstructed from the source alone.

```text
Project/
├── Project Plan.md
├── .Project Plan.doxmind
├── Reference.html                  # ordinary Attachment; no sidecar
├── Research Report.pdf
├── .Research Report.pdf.doxmind   # legacy recovery evidence
├── Quarterly Plan.xlsx
└── .Quarterly Plan.xlsx.doxmind  # legacy recovery evidence
```

## What each file contains

| Item | Source of truth | Hidden sidecar |
| --- | --- | --- |
| Markdown Page | The document text in `.md` or `.markdown` | Lossless rich-editor HTML and replaceable doXmind-only state |
| Ordinary Attachment | The original PDF, spreadsheet, or HTML file | None is created by current releases |
| Legacy PDF or spreadsheet | The original Attachment | Historical edit state created by an older release; recovery evidence only |

For a Markdown Page, the filename extension is removed from the sidecar name. Older PDF and spreadsheet sidecars retain the source extension in their names.

## Keep source and sidecar together

Keep a Page and its sidecar together when you want full editor fidelity. The app does this automatically when you manage Pages from the workspace sidebar. If you use Finder or another tool, include the hidden sidecar yourself.

<Warning>
  If an older release created a PDF or spreadsheet sidecar, keep the source, sidecar, `.bak`, `.lock`, and `.corrupt-*` files together. Current recovery attempts never make those files disposable.
</Warning>

## Other local files

- A `.doxmind` folder inside a workspace can hold local workspace metadata.
- A `<sidecar>.lock` file coordinates migration. It is small, can remain afterward, and should not be deleted manually.
- A `<sidecar>.bak` file is a copy of the pre-migration sidecar.
- A `<sidecar>.corrupt-*` file preserves unreadable data for recovery.
- App-level settings and metadata live under `~/.doxmind`, separately from document content.

For an everyday backup, preserve the full workspace folder, including hidden files. The current recovery flow inspects only the main legacy sidecar and `.bak`; it does not consume `.lock` or `.corrupt-*` evidence. Do not move a backup over the main sidecar before an attempt, and do not manually replace or delete evidence.

## Privacy and network access

doXmind does not upload documents, provide cloud sync, or require an account. Update checks contact the release service. A web bookmark preview directly requests the target page and referenced images from your Mac. Document storage remains local.

Folders stored in iCloud Drive, Dropbox, or another synced location can still be uploaded by that provider according to its settings.
